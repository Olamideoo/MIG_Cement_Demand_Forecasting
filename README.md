# MIG Cement Demand Forecasting

Weekly cement demand forecasting and reorder planning for Midlands Infrastructure
Group's 30 construction sites — from raw operational records through to a deployed
API and operations dashboard.

**Live:** [Dashboard](http://13.59.81.166/) · [API docs](http://13.59.81.166/api/docs) · [Model tracking](http://13.59.81.166/mlflow/)


---

## The problem

MIG pours concrete across 30 sites. Each site holds cement in a silo and orders
replenishment against a planned pour schedule. Ordering against the *schedule* rather
than against *consumption* was producing a specific and expensive failure:

- Sites were ready to pour on only **45% of days a pour was planned**
- **20.6% of delivered cement was rejected at the silo** for lack of headroom
- Silos sat **jammed or starved 68% of site-days** — only 18% in a workable 20–80% band

Not a shortage. A timing and distribution problem — cement in the wrong silo on the
wrong day. The brief: forecast demand up to 8 weeks ahead, at ≤ 15% error, and use it
to drive reordering.

## What we built

A forecast of weekly cement consumption per site, and an inventory policy driven by it.
Simulated over the same eight weeks as the figures above:

| | Recorded practice | Forecast-driven policy |
|---|---:|---:|
| Pour readiness | 45% | **99.9%** |
| Cement ordered | 42,549 t | **32,924 t** |
| Unmet pour | 10,684 t | **18 t** |
| Deliveries rejected | 8,755 t | **0 t** |

Less cement ordered *and* better service — the reduction comes from not buying cement
that was previously rejected or left sitting in the wrong place.

## Model outcome

| Metric | Result | Target |
|---|---|---|
| Hold-out MAPE | **12.77%** | ≤ 15% ✅ |
| Hold-out RMSE | 30.57 t per site-week | — |
| Hold-out bias | +1.92 t (slight over-forecast) | near zero ✅ |
| Sites individually within 15% | 18 of 30 | — |

Random forest, 300 trees, weekly grain per site. Trained on 3 Jan 2022 – 30 Sep 2024
(4,320 site-weeks); tested on the 240 site-weeks that follow, never seen in training.

Two findings worth knowing:

- **Accuracy does not decay with horizon** (week 1: 14.6%, week 8: 9.8%). The model
  leans on the planned pour schedule, which is known in advance — so an 8-week forecast
  is as trustworthy as a 1-week one.
- **The model cannot extrapolate.** Ask it about a pour larger than a site has ever
  done and it returns a value borrowed from other sites. `/predict` detects this and
  returns the site's real pour range alongside a warning.

Full findings, limitations and open assumptions: **[REPORTS/final_report.md](REPORTS/final_report.md)**

## Architecture

```
SQLite ──> clean ──> weekly panel ──> random forest ──┬──> MODELS/*.joblib
                                                      └──> MLflow run + registry
                        │
                        ├──> FastAPI  ──> /health /forecast /predict /inventory
                        │                        │
                        └──> Streamlit dashboard ┘  (reads the API when deployed)
```

Training and serving import the same `features/build.py`, so the features a prediction
is made from cannot drift from the features the model was trained on.

Four containers, one compose file: `model` (training job), `api`, `dashboard`, `mlflow`.
In deployment nginx fronts all three services on port 80.


## Running it

```bash
pip install -r requirements-dev.txt && pip install -e .
python -m mig_cement.pipeline        # train (~90s)
make api                             # http://localhost:8000/docs
make dashboard                       # http://localhost:8501
make mlflow                          # http://localhost:5000
make test                            # 46 tests
```

Or the whole stack in containers:

```bash
docker compose -f docker/docker-compose.yml up -d --build mlflow
docker compose -f docker/docker-compose.yml run --rm --build model
docker compose -f docker/docker-compose.yml up -d --build
```

Order matters: `DATA/processed/` is gitignored, so the training job must run before the
API starts or it falls back to a single estate-wide error estimate instead of per-site
values — which silently changes every reorder point.

The dashboard calls the API when `API_BASE_URL` is set and loads the model directly
otherwise. There is no silent fallback between the two; the sidebar states which is live.

## Engineering

- **46 contract tests** over the HTTP surface, including that the API reproduces the
  12.77% hold-out figure and that the extrapolation guard is per-site, not estate-wide
- **CI** lints, trains, runs the suite and builds all three images on every push
- **MLflow** records every training run — parameters, both metric sets, version tags,
  artefacts and the registered model
- **scikit-learn is pinned** because the model is a pickle; unpickling under a different
  version can change predictions silently
- Containerised training reproduces local training exactly (12.77% / 30.57 t / reload
  verified to 1e-13)

## Status and limitations

Deployed and working. Known constraints, in full in the
[final report](REPORTS/final_report.md):

- Accuracy is measured on **held-out history**, not live operation. Forecasting future
  weeks needs the pour schedule for those weeks, which MIG already produces.
- **No cost data exists** in the source system, so all impact is stated in tonnes and
  days rather than money.
- **Lead time (3 days) and service level (~98%) are assumptions**, not facts from the
  data. Every reorder point depends on them.
- Weather is not an input, though rainfall above ~25 mm/day raises no-pour days from
  9% to 68%.
